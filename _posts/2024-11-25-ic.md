## Impression Counter: fast

이전에 다니던 회사 버즈빌에서는 광고의 소재별로 impression cap 기능이 존재했었다.
한명당 N번이상 광고를 보면 더이상 할당하지 않는 기능인데, 이러한 기능은 많은 회사들에서
필요한 기능으로 보인다. 특정 소재를 몇번 보았는지, 특정 소재를 몇번 클릭했는지를 가져와서
적절한 소재를 내려주는 것은 전통적인 추천 로직의 기반이 된다. 그러나 추천로직에서의 imp/click
횟수는 꽤나 어려운 데이터인데, 여러 소재들의 imp/click 횟수를 가져와야하기 때문이다.

최적화 하는 방법은 여러가지가 있다. 소재가 100개가 있다면 100개의 소재에 대한 데이터를
가져와서 필터링하는 방법, 그리고 유저가 최근에 활동한 내역을 가져와서 필터링하는 방법이다. 두가지
방법은 전부 상호보완적인데, 소재가 많아질수록 첫번째 방법이 불리해지며, 유저가 행동하는 것들이
많아질수록 두번째 방법이 불리해진다. 또한 두가지 방법 모두 소재를 가져오는 과정에서 필터링하는 로직이 어디에 들어가는지에 따라서 부하가 어디에 집중되는지가 결정된다.

간단한 함수를 하나 만들어서 우리의 요구사항을 표현해보겠다. 유저에 대하여 활동 기록에 따라서
주어진 컨텐츠들중에 조건에 맞는 것들만 필터링하는 함수이다.

```go
func (s Service) FilterContent(
	u User, contents []Content,
	impCap, clickCap int,
) ([]Content, error) {
	// write logic
	return []Content{}, nil
}
```

매우 간단하고, 쉬운 기능처럼 보이겠지만 유저가 많아지고 컨텐츠가 늘어나면 그에따라서
부하는 늘어난다. 우리는 어디에 부하가 걸리는지, 그리고 그 지점을 이곳 저곳으로 옮기면서
시스템을 최적화해보겠다.

### user의 상태를 저장하고, 가져오는 방식

버즈빌에서는 dynamo db(앞으로는 그냥 dynamo라고 부를것임)를 많이 사용해서 시스템을 개발했는데, 개인적으로는 dynamo를 매우 잘 사용하는
팀이었다. 나의 희미한 기억에 따르면 dynamo와 es를 사용해서 광고의 필터링을 진행하였다.
대략적인 로직은 다음과 같다.

```go
func (s Service) Impression(u User, content Content) {
    // imp하는 시점에 dynamo에 row를 하나 쌓는다.
    saveToDynamo(u, content)
}

func (s Service) FilterContent(
	u User, contents []Content,
	impCap, clickCap int,
) (Filter, error) {
    // dynamo에서 range query를 한다
	imps := getRecentImpressions(u)

    // es query에 impression 정보들을 넣어서 필터링
    return addFilter(FrequencyCap, imps)
}
```

위 방식을 평가해보자면, impression되는 시점의 연산은 꽤나 가볍다. 당연히 추천보다는
컨텐츠를 보는 것이 압도적으로 트래픽이 많을 것은 자명하기 때문이다. 하지만 할당하는 시점의
부하는 꽤나 큰데, range query는 일단 scan해야하는 양이 많을 수 밖에 없으며, 유저의
활동량이 늘어나면 선형적으로 모든 비용이 증가한다. 반환하는 데이터, serialize, network 등등...

그리고 filtering하는 로직이 es에서 처리되고 있는데, 이는 꽤나 좋지 않은 방식이다.
es는 요청을 분산해서 처리 가능하고, 아무리 빠르다고는 하지만 어플리케이션 서버보다는
scale out이 힘들다. 그러니 만약 현재 운영중인 컨텐츠가 몇천만건이 넘지 않는다면
local cache를 이용하고 최대한 application에서 미리 처리하는 것이 빠를 것이다.
local cache에서 현재 imp 횟수를 넘어서 필터링해야하는 id들을 만들어두고 es query에서는
그 id들을 제외하는 방식을 사용하면 es에서 계산하는 것을 application으로 옮겨올 수 있다.

### dynamo 헤이터

미리 이야기해두자면, 나는 dynamo를 매우 싫어한다. 일단 느리고, 오버헤드가 크다.
http/s 레이어를 거쳐서 접근하는건 DB가 아니라 웹서버다. throughput이 바로
증설되지 않아서 천천히 올리거나 jitter, 혹은 미리 cap을 조정하는건 정말로 웹서버의
특징이다. 그러니 되도록이면 쓰지 말도록 하자.

하지만 이 구현의 천재적인 점은 dynamo를 사용하였기에 range query를 사용할 수 있다는
점이다. 만약 row by row로 유저의 횟수를 db에서 들고왔어야한다면 아마 꽤나 큰 연산이
필요했을 것이다. scan하는 양도 많고, scale out도 힘들고, insert도 많으면 rw db에
부하는 더욱 가해졌을 것이다. rate limit을 걸고 insert를 한다고해도 샤딩이 필요할정도로
트래픽이 많으리라.

간단히 redis를 사용해서 구현해보겠다. 만약 위 로직을 똑같이 구현한다면 ZSET을
이용하는게 제일 비슷할 것이다. ZSET의 시간복잡도는 O(log(SET_LEN) + RETURN_EL_LEN)인데,
이는 유저의 행동이 많아지면 많아질수록 늘어나며, set의 크기에 따라서도 늘어난다. 여전히
시간에 대한 계산과 행동이 많아질수록 부하는 db(redis)에 집중된다. 이 부하를 application으로 가져와보겠다.

#### SO_REUSEPORT

fiber / fasthttp는 prefork하는 option으로 multi process 처리를 지원하는데,
벤치마크에서 이 기능을 사용해서 여러 프로세스가 동시에 요청을 받을 수 있도록 한다. 즉 요청이
들어왔을 때 listen thread가 아닌 여러 스레드에서 요청을 받아서 처리할 수 있기에 성능 향상이
된다는 주장이다.

하지만 매우 치명적인 단점이 있는데, fork를 하는 순간부터 golang runtime은 혼란에 빠지고,
메모리는 더 많이 사용할 것이고, monitoring 도구는 각각의 local state를 동기화 하지 못하고
thread를 하나씩밖에 사용할 수 없기에 gc와 같은 background 작업에 요청을 처리하는 thread가
block될 수 있다. 그러니 되도록이면 쓰지 말고, static한 application에서만 쓰자.

nginx에서는 socket sharding을 통하여 성능 향상이 있다고 이야기하지만, 그것은 runtime이
따로 존재하지 않는 구현체이기도 하고 application이 아니기에 외부 디펜던시나 local static state도
거의 없다.
